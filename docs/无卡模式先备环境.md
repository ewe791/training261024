# 无卡模式：先把环境备好，等有卡再开训

> 适用：还没租到/还没排到 GPU，但想先把代码传上去、依赖装好、模型下好。
> 全程不需要 GPU，**约 40–60 分钟，成本约 1 毛钱**（主要是下载模型的带宽时间）。
> 有卡之后只需要 3 条验证命令 + 1 条训练命令。

---

## 0. 先看分工：什么能提前做，什么必须等卡

| 事情 | 需要 GPU 吗 | 无卡模式能做吗 | 备注 |
| --- | --- | --- | --- |
| 传代码、解压 | 不需要 | ✅ | 走 SSH / JupyterLab |
| 装 Python 依赖 | 不需要 | ✅ | 镜像自带 CUDA 版 torch，只补上层库 |
| 下载基座模型（15.2 GB） | 不需要 | ✅ | 这一步最花时间，正好用无卡时段做 |
| 造数据、划分、训练数据体检 | 不需要 | ✅ | 纯 CPU，30 秒 |
| 单元测试（28 条） | 不需要 | ✅ | 纯 CPU |
| **正式训练** | **需要** | ❌ | 无卡模式没有 GPU，会在加载模型后报错 |
| **真实模型评测** | **需要** | ❌ | 7B 推理在 CPU 上慢到没有意义 |

一句话：**除了训练和评测，其他全部可以提前做完。** 训练前那 40 分钟最容易被浪费在“等下载、等 pip”上，无卡时段正好覆盖掉。

### 0.1 先明确一件事：要“传上去”，得先有一台机器

云上没有实例，就没有地方可传。无卡模式的意思是「**已经开了一台实例，但暂时不占 GPU**」，
不是「不用开机器」。所以第 1 步一定是先开一台无卡实例（¥0.1/小时）。

**连实例都不想开**（比如白天上班、晚上才训练）也没关系，下面这些在本机就能做，
而且**不需要装 torch**（纯标准库）：

```bash
python scripts/build_dataset.py      # 造数据
python eval/split_dataset.py         # 划分 + 泄漏检查
python train/finetune_lora.py --dry-run   # 训练数据体检（样本数 756）
python -m unittest discover -s tests -t .  # 28 条单测
python scripts/run_all.py --skip-build     # stub 后端跑完整评测与报告（模拟值，非真实成绩）
```

只有两件事必须在云上做：**下载 15 GB 基座模型**、**真实训练/评测**。
（本机也不是完全下不了模型，只是 8 GB 显存跑不动 7B 训练，见速查手册附录 E。）

## 1. 开一台「无卡模式」实例

### 1.1 AutoDL 的操作路径

1. 登录控制台 → 「容器实例」→「租用新实例」或选一台已关机实例
2. 关机状态下，实例操作栏里点 **「无卡模式开机」**
   （不同版本可能叫「无卡开机」/在「更多」下拉里；找不到就在实例操作里翻一遍）
3. 计费约 **¥0.1/小时**，不占用 GPU，所以不用排队

> 其他平台也有等价模式：阿里云 PAI 的「CPU 开发模式」、腾讯 HAI 的「仅 CPU」、恒源云「无卡开机」。
> 找不到这个功能时，选**最便宜的 CPU 实例**也能达到同样目的（但要注意：CPU 实例通常没有数据盘，见第 2 节）。

### 1.1.1 顺便把镜像选对（只选这一次）

在创建/更换镜像的界面里，四列是级联的：框架 → 版本 → Python → **CUDA**。

| 选什么 | 值 |
| --- | --- |
| 框架 | PyTorch |
| 版本 | 2.8.0（任意 ≥2.2 都行） |
| Python | 3.12（或 3.10 / 3.11） |
| CUDA | 它提供的那个（通常 12.8） |

**CUDA 列不能反着挑**：它只列出这个 PyTorch 版本实际发布过的 CUDA 构建。
找不到 CUDA 13 是正常的（torch 的 wheel 永远滞后于 CUDA 发布），而且**你不需要**它。
判断规则只有一条：`torch 编译的 CUDA ≤ nvidia-smi 里的 CUDA` 就能跑。
RTX 50 系（sm_120）例外，它必须 cu128 + torch ≥2.7。

完整解释（含 torch↔CUDA 对照表、驱动 CUDA 与 torch CUDA 的区别）见
[`上云训练详细操作手册.md`](上云训练详细操作手册.md) 第 3.2 节。

### 1.2 无卡模式下 GPU 命令的“假故障”

开机后执行 `nvidia-smi`，你会看到：

```
NVIDIA-SMI has failed because it couldn't communicate with the NVIDIA driver.
```

或者

```
No devices were found
```

**这是正常的，不是环境坏了。** 无卡模式本来就没把 GPU 分配给你，驱动也就不用加载。
等换成有卡开机，同一条命令会正常列出显卡。

### 1.3 检查点

```bash
python3 -V          # 3.8+ 都行，项目要求 3.10+
df -h               # 看清楚有哪些盘、各剩多少
ls /root/autodl-tmp # 数据盘目录存在就说明挂上了
```

## 2. 先搞清楚两个盘（这一步决定你要不要重来）

| | 系统盘 | 数据盘 |
| --- | --- | --- |
| 典型路径 | `/root`（含 `/root/miniconda3`） | `/root/autodl-tmp` |
| 容量 | 30 GB 左右，随镜像 | 按需购买（建议 ≥30 GB） |
| 关机后 | 保留 | 保留 |
| **释放实例后** | **清空** | **清空** |
| **换卡型 / 迁移到别的机器** | **可能重置回初始镜像** | **保留** |

最后一行是本手册存在的原因：你很可能**先租 A 卡准备环境，后来换成 B 卡**（或者同一卡型换到别的机器）。
一旦系统盘重置，`pip install` 装的包、`/root/xxx` 下的文件全没了，只有数据盘的东西还在。

所以规划成这样，怎么换卡都不用重做：

```
/root/autodl-tmp/
├── ft-kb-4.1/              ← 项目代码（脚本、配置、数据）
│   ├── .venv/              ← 虚拟环境（放这里！放系统盘会随重置消失）
│   ├── .env                ← 配置（同样放项目内）
│   └── ...
└── Qwen2.5-7B-Instruct/    ← 基座模型 15.2 GB
```

如果你已经不小心把项目放在 `/root/ft-kb-4.1` 了，两条命令搬过去：

```bash
mv /root/ft-kb-4.1 /root/autodl-tmp/ft-kb-4.1
# 虚拟环境里写死了绝对路径，搬完要重建（见 4.2）
rm -rf /root/autodl-tmp/ft-kb-4.1/.venv
```

## 3. 传代码上去

### 3.1 本地打包（Windows 用 Git Bash，不要用 CMD/PowerShell 的 tar）

```bash
cd "/e/Desktop/微调"
bash scripts/make_bundle.sh
# 输出形如：
# 包:    dist/ft-kb-4.1-20261024-1356.tar.gz
# 大小: 248K
# 校验: <64 位十六进制>
```

为什么强调用 Git Bash：Windows 自带的 `tar.exe` 对 UTF-8 文件名处理不一致，打出来的包在 Linux 上解压，中文文件名可能变乱码（`docs/上云训练详细操作手册.md` 会变成问号）。Git Bash 的 tar 是 GNU 版本，没有这个问题。

### 3.2 上传

```bash
# 端口是五位数，注意 scp 是大写 -P（小写 -p 是保留时间戳，写错了连不上还不报错）
scp -P 12345 dist/ft-kb-4.1-20261024-1356.tar.gz root@connect.xxxx.seetacloud.com:/root/autodl-tmp/
```

连接信息在实例详情页的「登录指令」里，格式是：

```
ssh -p 12345 root@connect.xxxx.seetacloud.com
```

照着把 `ssh` 换成 `scp`，末尾加上「本地文件 目标路径」就行。

### 3.3 解压（在实例里执行）

```bash
mkdir -p /root/autodl-tmp/ft-kb-4.1
tar xzf /root/autodl-tmp/ft-kb-4.1-*.tar.gz -C /root/autodl-tmp/ft-kb-4.1
cd /root/autodl-tmp/ft-kb-4.1
ls
```

**检查点**：应该看到 `START_HERE.md README.md common config data docs eval requirements.txt scripts tests train`。

包内**没有** `data/*.jsonl`（数据集 10 秒重建）也**没有** `.env`（要按你自己的路径生成），这两样在第 5、6 步做。

### 3.4 不想用命令行？

JupyterLab 页面左侧文件树，拖进 `/root/autodl-tmp/`，然后开一个 Terminal 解压，效果一样。
缺点：248 KB 还行，如果以后要传 15 GB 的模型就不适合了。

## 5. 不想用脚本：分步做

### 5.1 装依赖

```bash
cd /root/autodl-tmp/ft-kb-4.1
bash scripts/cloud_setup.sh --no-card
```

这个脚本有两个关键设计，值得知道为什么：

**① 不装 torch。** 云镜像（AutoDL/PAI/HAI）里的 torch 是配好 CUDA 的。你 `pip install torch` 会拉 2 GB 以上，而且默认源给的可能是 CPU 版——装完 `torch.cuda.is_available()` 变成 `False`，你还以为是卡坏了。

**② venv 用 `--system-site-packages` 创建。** 否则 venv 是隔离的，看不到镜像的 torch，`pip install peft` 时 pip 认为 torch 缺失，会**自己再装一个**。这就是很多人“明明镜像有 torch，训练却报 no CUDA”的真正原因。

预期输出（版本号会不同，`True/False` 都正常——无卡时必然 False）：

```
== 1/6 检查 Python ==
Python 3.12.3
解释器：/usr/bin/python3

== 2/6 准备虚拟环境 ==
已创建 .venv（--system-site-packages）
已激活：/root/autodl-tmp/ft-kb-4.1/.venv/bin/python

== 3/6 确认 torch 可见（只检查，不安装）==
torch 2.4.0 | CUDA 编译版本 12.1 | cuda.is_available=False
（无卡模式下 is_available=False 是正常的）
...
  OK   transformers   4.46.3
  OK   peft           0.13.2
  OK   datasets       3.1.0
  OK   accelerate     1.1.1
  OK   sentencepiece  0.2.0
  OK   modelscope     1.20.0
```

如果第 3 步就报 `[失败] 当前解释器里 import torch 失败`，99% 是 venv 建错了：

```bash
rm -rf .venv && bash scripts/cloud_setup.sh --no-card
```

## 6. 无卡自检：确认“只差一张卡”

```bash
.venv/bin/python scripts/check_env.py --no-card
```

`--no-card` 是必须的。不加的话，脚本会把「没有 GPU」报成阻塞项（它在有卡环境下确实该报），你会以为环境有问题：

```
[BLOCK] GPU   torch.cuda.is_available() = False（驱动/镜像不对，或选了 CPU 实例）
```

加上之后，预期结尾是：

```
结论：环境已就绪（无卡模式，GPU 相关项已跳过；4 项提示）
      有卡开机后执行：python scripts/check_env.py   再确认一次，然后即可开训
```

那几项提示通常是「`.env` 未找到」（如果你还没建）、「PYTHONIOENCODING 未设置」之类，不影响训练。

## 10. 故障排查（无卡阶段专属）

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| `nvidia-smi: command not found` 或 `No devices were found` | 无卡模式本来就没 GPU | 正常，忽略；有卡开机后再看 |
| `check_env` 报 GPU 阻塞，其他都绿 | 没加 `--no-card` | `python scripts/check_env.py --no-card` |
| venv 里 `import torch` 失败 | venv 没加 `--system-site-packages`，隔离了镜像 torch | `rm -rf .venv && bash scripts/cloud_setup.sh --no-card` |
| 装完依赖 `cuda.is_available()` 变 False（有卡时） | pip 顺带装了 CPU 版 torch | 见下方「修复 CPU 版 torch」 |
| `modelscope: command not found` | 没激活 venv，PATH 里只有系统命令 | 用 `.venv/bin/modelscope ...` 或先 `source .venv/bin/activate` |
| 模型下到一半断 | 网络抖动 | 重跑同一条命令，会续传 |
| `No space left on device` | 下到系统盘了 | 检查 `--local_dir` 是不是 `/root/autodl-tmp/...` |
| `python: can't open file 'scripts/build_dataset.py'` | 不在项目根目录 | `cd /root/autodl-tmp/ft-kb-4.1` |
| 换了卡型后 `pip list` 里依赖全没了 | 系统盘被重置 | 无卡阶段把 venv 建在项目内（数据盘）就不会有这个问题；否则重跑一次 `cloud_setup.sh` |
| 有卡开机后 `torch.cuda.is_available()` 仍 False | 驱动与 torch CUDA 版本不匹配（常见于 50 系新卡） | 见下方「修复 CPU 版 torch」 |

### 修复 CPU 版 torch（有卡环境）

```bash
pip uninstall -y torch torchvision torchaudio
# 按驱动选：cu121 / cu124 / cu128（RTX 50 系必须 cu128）
pip install torch --index-url https://download.pytorch.org/whl/cu121
```
