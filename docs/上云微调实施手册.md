# 上云微调实施手册

> 适用对象：本项目（4.1 知识库 Agent 微调）从本地流转到云端 GPU 执行。
> 读者假设：会敲命令行，没做过云 GPU 训练也行——每一步都给了命令、预期输出和卡住时的处理。
> 卡型以 **单卡 24G（4090 / 3090）** 为主线，16G 与 A100 的差异单独标注。

---

## 0. 先看这张表：整件事要几步、多久、花多少钱

| 步骤 | 动作 | 耗时 | 产出 |
| --- | --- | --- | --- |
| 1 | 选卡型、开实例 | 10 分钟 | 可 SSH 的机器 |
| 2 | 传代码 | 5 分钟 | `/root/autodl-tmp/ft-kb-4.1` |
| 3 | 装环境 | 5–10 分钟 | `.venv` + 依赖 |
| 4 | 下基座模型 | 15–40 分钟（看带宽） | 约 15 GB 权重 |
| 5 | 环境自检 | 1 分钟 | `check_env.py` 全绿 |
| 6 | 造数据 | 10 秒 | 训练 756 条 / 测试 306 条 |
| 7 | 训练（3 epoch） | 1–1.5 小时 | LoRA adapter（约 80 MB） |
| 8 | 评测（基座 + 微调） | 20–35 分钟 | `results_*.json` |
| 9 | 出报告 | 5 秒 | `reports/eval_finetune.md` |
| 10 | 拉回产物、停机 | 10 分钟 | 本地归档 |

**合计约 3–5 小时**（下载占大头）。按 4090 约 ¥1.5–3/小时、A100 40G 约 ¥5–10/小时估算，
单次总成本大致 **¥10–40**（以平台实时价为准，不要按这里的数字报销）。

### 最短路径（已经熟的话，直接抄这 8 条）

```bash
# 在云实例上，项目已传到 /root/autodl-tmp/ft-kb-4.1
cd /root/autodl-tmp/ft-kb-4.1
bash scripts/cloud_setup.sh --no-venv                      # 1 装环境

python train/finetune_lora.py                               # 7 训练
python scripts/run_all.py --backend local --skip-build       # 8 评测+报告
#    注：local 后端下 run_all 会自动把「基座 / 微调」拆成 4 个进程分别评测，
#        避免两个 7B 模型同时驻留显存；单卡 24G 也能跑完
```

## 1. 选卡型：先算显存，再挑便宜

本项目训练的是 **Qwen2.5-7B-Instruct + LoRA（rank 16）**，不是全参微调，显存需求主要来自「权重 + 激活」：

| 方案 | 权重 | 激活（seq 2048, bs1, 梯度检查点） | 合计 | 适用卡 |
| --- | --- | --- | --- | --- |
| bf16 LoRA | ≈ 14 GB | ≈ 4–6 GB | **18–20 GB** | 24G：4090 / 3090 / L20 |
| 4bit QLoRA | ≈ 4.5 GB | ≈ 3–4 GB | **8–10 GB** | 16G：4080 / 3080Ti / A10 |

| 卡型 | 训练建议 | 训练耗时（756 条 × 3 epoch） | 评测 |
| --- | --- | --- | --- |
| RTX 4090 24G | 默认配置，`batch_size: 1` | 60–90 分钟 | 可直接 fp16 评测（单进程单模型） |
| RTX 3090 24G | 同上 | 90–120 分钟 | 同上，稍慢 |
| A100 40G | `batch_size: 2` | 35–50 分钟 | 最省心 |
| 4080 / A10 16G | **必须开 4bit**（见 6.3） | 120–150 分钟 | 评测需 `FTKB_LOAD_4BIT=1` |
| T4 / V100 16G | 不建议（无 bf16、带宽低） | 4 小时以上 | 仅应急 |

**结论**：想省事就租 4090 24G；想快就 A100 40G；手上有 16G 卡也能跑，把 4bit 打开。

> 别用“CPU 实例”或“无卡模式”做训练，只适合传文件、造数据、看日志。
> **无卡阶段具体怎么操作**（含“系统盘会重置，venv 必须放数据盘”）：
> [`无卡模式先备环境.md`](无卡模式先备环境.md)，一条命令 `bash scripts/nocard_prepare.sh`。

## 2. 开实例：三件事别选错

1. **镜像**：选 `PyTorch 2.x + CUDA 12.x + Python 3.10/3.11` 的官方镜像。
   自带 torch 就行，本项目**不重装 torch**（重装容易把 CUDA 搞坏，还多下几个 G）。
2. **数据盘**：至少留 **30 GB**（模型 15G + 中间权重 + adapter）。国内平台一般是 `/root/autodl-tmp` 这类独立数据盘，**项目一定放在数据盘**，别放系统盘。
3. **计费方式**：
   - 按量计费：训练完就关机，最省钱，适合一次性跑完。
   - 竞价/抢占实例：便宜但**会被回收**，必须先看第 7.4 节的续训设置。
   - 关机后 GPU 不计费，但**数据盘通常继续计费**；产物拉回本地后可以直接释放实例。

```bash

```

## 7. 环境自检（这一步别跳）

```bash
python scripts/check_env.py
```

输出分三档，逐行看：

| 标记 | 含义 | 处理 |
| --- | --- | --- |
| `OK` | 正常 | — |
| `WARN` | 不阻塞，但会影响体验/精度 | 例如 `.env` 没建、显存 <15G 建议开 4bit |
| `BLOCK` | 阻塞，必须修 | 按提示装依赖 / 改路径 / 换镜像 |

期望结尾：**`结论：可以开训`**。

常见 BLOCK 与处理：

| 报错项 | 原因 | 处理 |
| --- | --- | --- |
| `PyTorch 未安装或导入失败` | 镜像没选 PyTorch 版 | 换镜像重开实例 |
| `GPU torch.cuda.is_available() = False` | 驱动/CUDA 不匹配 | 换镜像；`nvidia-smi` 看是否识别到卡 |
| `依赖 peft 缺失` 等 | setup 没跑或跑失败 | 重跑 `cloud_setup.sh`，看 pip 报错 |
| `基座模型路径 不存在` | 模型没下完 / `.env` 路径错 | 回到第 6 步 |
| `未找到 *.safetensors` | 下载中断 | 删目录重下 |

## 9. 训练前体检（不加载模型，10 秒）

```bash
python train/finetune_lora.py --dry-run
```

期望：

```
样本数: 756
```

## 10. 正式训练

### 10.1 启动

```bash
cd $PROJ
mkdir -p logs
nohup python train/finetune_lora.py > logs/train.log 2>&1 &
tail -f logs/train.log
```

不用 `nohup` 的话，SSH 一断训练就没了；也可以用 `tmux new -s train`。

**基座路径怎么取的**（容易踩）：优先级是

```
--base-model 参数  >  .env 里的 FTKB_BASE_MODEL_PATH  >  config/lora_sft.yaml 的 base_model
```

`config/lora_sft.yaml` 里写的是 HF 模型 ID（`Qwen/Qwen2.5-7B-Instruct`）。
只要 `.env` 里配了本地目录，训练和评测就都用本地权重，不会再联网下一次 15 GB。

启动后**第一屏必须有这一行**，且是本地目录：

```
基座模型: /root/autodl-tmp/Qwen2.5-7B-Instruct
```

如果打印的是 `Qwen/Qwen2.5-7B-Instruct`，说明 `.env` 没生效——立刻 `Ctrl+C` 停掉，
检查 `.env` 是否在 `$PROJ` 根目录、变量名是否拼错。**不要让它开始下载**，10 分钟白等。

想显式指定也可以直接传参（不依赖 .env）：

```bash
python train/finetune_lora.py --base-model /root/autodl-tmp/Qwen2.5-7B-Instruct
```

### 10.2 盯三个数

```bash
watch -n 5 nvidia-smi          # 显存占用 / GPU 利用率
grep -E "loss|epoch" logs/train.log | tail -20
```

| 现象 | 判断 |
| --- | --- |
| 显存 20–22 GB / 24G 卡 | 正常，接近上限但没爆 |
| `torch.OutOfMemoryError` | 见 10.3 |
| loss 从 1.x 降到 0.3–0.6 并趋稳 | 正常收敛 |
| loss 一直 0.0 或 NaN | 学习率太大 / 数据有问题，先看 8 步的自检 |
| 前 2 分钟 loss 几乎不动 | 正常，LoRA 初期在适应 |

### 10.3 显存不够：按这个顺序调（一次只改一项）

1. `config/lora_sft.yaml` → `batch_size: 1`（已经是 1 就下一步）
2. `max_length: 2048` → `1536`（先看 dry-run 的截断数，别截太多）
3. `load_in_4bit: true`（显存直接降到 8–12G，速度慢 30% 左右）
4. 还不行 → 换 24G 卡

改完重跑，**别在 OOM 的进程里直接改参数**，先 `nvidia-smi` 确认显存已释放
（有残留就 `pkill -f finetune_lora`）。

### 10.4 竞价实例被回收后怎么续

前提：`config/lora_sft.yaml` 里 `save_steps: 200`（默认），会往 `outputs/lora-knowledge-agent-4.1/checkpoint-*` 存检查点。

```bash
ls outputs/lora-knowledge-agent-4.1/          # 确认有 checkpoint-xxx
python train/finetune_lora.py --resume        # 从最新检查点续
```

### 10.5 检查点：训练成功长什么样

```bash
ls -lh outputs/lora-knowledge-agent-4.1/
# 期望：adapter_config.json  adapter_model.safetensors（约 40–90 MB）
#       以及 tokenizer 相关文件、trainer_state.json
```

体积只有几十 MB 是对的——**LoRA 只存增量**，不是 15G 的整模型。

## 11. 合并权重：两条路，按需要选

| | 直接用 adapter（推荐） | 合并成整模型 |
| --- | --- | --- |
| 命令 | 什么都不用做 | `python train/merge_lora.py ...` |
| 体积 | 几十 MB | 约 15 GB |
| 加载 | `FTKB_ADAPTER_PATH` 指过去 | 当成普通模型目录 |
| 速度 | 略慢 2–5% | 稍快 |
| 何时用 | 评测、交付、换机器 | 要给别人一个“单目录即可跑”的模型 |

```bash
# 仅在确实要合并时执行
python train/merge_lora.py \
  --base-model /root/autodl-tmp/Qwen2.5-7B-Instruct \
  --adapter outputs/lora-knowledge-agent-4.1 \
  --out outputs/merged-4.1
```

> **4bit 训练的 adapter 不要急着合并**：需要先反量化，peft 对 bnb 权重的合并有坑。
> 用 4bit 训练的就直接走 adapter 那条路评测。

## 12. 评测：把 stub 数字换成真实数字

### 12.1 先清掉旧的模拟结果（重要）

```bash
rm -f eval/results_*.json eval/results_*.jsonl eval/compare.json reports/*.md
```

不清的话，脚本会检测到 `backend=stub` 的结果与本次不一致而拒绝合并（这是故意设计的守卫），你会看到提示但拿不到完整对比表。

### 12.2 分两个进程跑（省显存）

```bash
# 基座
python eval/test_tool_calling.py --role base
python eval/test_answer_quality.py --role base

# 微调
python eval/test_tool_calling.py --role finetuned
python eval/test_answer_quality.py --role finetuned
```

为什么分两个进程：一个 7B 模型 fp16 约占 15G，**同进程先后加载基座和微调容易显存碎片导致 OOM**；
两个独立进程，前一个退出即释放。

> 也可以直接 `python scripts/run_all.py --backend local --skip-build`：
> 这个脚本在 `--backend local` 时会自动按上面四步拆成独立进程执行，然后再出对比与报告。

- 16G 卡：两处命令前都加 `FTKB_LOAD_4BIT=1`，例如
  `FTKB_LOAD_4BIT=1 python eval/test_tool_calling.py --role base`
- 每步 5–10 分钟，四步共 20–35 分钟。

### 12.3 检查点

```bash
python - <<'EOF'
import json
for f in ("tool_calling","answer_quality"):
    d=json.load(open(f"eval/results_{f}.json",encoding="utf-8"))
    print(f, d["backend"], d["testset"]["total"], d.get("base"), d.get("finetuned"))
EOF
```

- `backend` 必须是 **`local`**（不是 `stub`）
- 两个角色的指标都要有数字，不能是 `None`
- 数字**明显低于**本地 stub 的模拟值是完全正常的——那才是真实模型水平

### 12.4 常见问题

| 症状 | 原因 | 处理 |
| --- | --- | --- |
| `未设置 FTKB_BASE_MODEL_PATH` | `.env` 没配或没在项目根目录 | 回 3.2 |
| 微调角色报 `需要 FTKB_ADAPTER_PATH` | 适配器路径错 | 指向 `outputs/lora-knowledge-agent-4.1` |
| 生成的答案全是 JSON 残片/复读 | 模型没学会协议 | 正常现象，看指标就能反映；先确认 adapter 真的加载了 |

## 附录 E：本机显卡不够时怎么用（8G 笔记本示例）

先看结论，按显存对号入座：

| 本机显存 | 7B LoRA（bf16） | 7B QLoRA（4bit） | 建议 |
| --- | --- | --- | --- |
| ≥24 GB | 可行，1–1.5 h | 不必 | 本机直接训 7B |
| 16 GB | 不可行 | 可行，2–3 h | 4bit 训 7B |
| **8–12 GB** | 不可行 | **极限，大概率 OOM** | **本机训 1.5B 验证流程，7B 上云** |
| 无 NVIDIA 卡 / 集显 | 不可行 | 不可行 | 只能造数据 + 跑 stub 评测 |

> 判断依据：7B bf16 权重就要 14 GB，加上激活至少 18–20 GB；
> 4bit 权重 4.5 GB + 激活 3–4 GB + CUDA 上下文约 1 GB，8 GB 卡只剩不到 1 GB 余量，
> Windows 上还有桌面合成占用，很容易 `CUDA out of memory`。

### E.1 第 0 步：确认卡和驱动

```bash
python scripts/check_env.py        # 不装 torch 也能读到卡型号/显存
nvidia-smi
```

### E.2 RTX 50 系（Blackwell）的坑：必须装 cu128 的 PyTorch

RTX 5060/5070/5080/5090 是 **sm_120** 架构。用默认源装的 `torch`（cu121/cu124）会在启动时报：

```
RuntimeError: CUDA error: no kernel image is available for execution on the device
```

必须装 **CUDA 12.8 构建、且版本 ≥ 2.7** 的 PyTorch：

```bash
# Windows / Linux 通用
python -m pip install --upgrade torch torchvision torchaudio \
  --index-url https://download.pytorch.org/whl/cu128

# 国内加速（可能滞后于官方，装不到就用上面官方源）
python -m pip install --upgrade torch --index-url https://mirrors.aliyun.com/pytorch-wheels/cu128

# 验证
python -c "import torch;print(torch.__version__, torch.version.cuda, torch.cuda.is_available(), torch.cuda.get_device_name(0))"
# 期望：2.7+ 12.8 True NVIDIA GeForce RTX 5060 Laptop GPU
```

**下载慢怎么办（实测数据）**：官方源 `download.pytorch.org` 只有 **226 KB/s**，
cu128 的 Windows wheel 有 **3.46 GB**，单线程要 80 分钟。换阿里云镜像能到 720 KB/s，
再用**分段并发**（curl `-r` 切 6 段 + 拼接）可以压到 12 分钟：

```bash
URL="https://mirrors.aliyun.com/pytorch-wheels/cu128/torch-2.8.0%2Bcu128-cp312-cp312-win_amd64.whl"
SIZE=3461384651; N=6; CH=$(( (SIZE + N - 1) / N ))
for i in $(seq 0 $((N-1))); do
  S=$((i*CH)); E=$((S+CH-1)); [ $E -ge $SIZE ] && E=$((SIZE-1))
  curl -sS -L -r "$S-$E" "$URL" -o "p$i" &
done; wait
cat p0 p1 p2 p3 p4 p5 > torch.whl
pip install --no-deps ./torch.whl
```

（Linux 版把文件名里的 `win_amd64` 换掉；先 `curl -sSI` 看 `Content-Length` 确认大小。）

装完再补上层库。**顺序很重要**——`accelerate` 依赖 torch，如果 torch 还没装好就先装它，
pip 会从 PyPI 拉一个 **CPU 版 torch** 顶上，`cuda.is_available()` 直接变 False：

```bash
# ① 先确认 torch 是 CUDA 版
python -c "import torch;print(torch.__version__, torch.cuda.is_available())"   # 必须 True
# ② 再装上层库
python -m pip install -i https://pypi.tuna.tsinghua.edu.cn/simple \
  "transformers>=4.44,<5" "peft>=0.12" "datasets>=3,<4" "accelerate>=0.33" \
  sentencepiece python-dotenv openai
```

两个版本钉子（2026-10 实测，不钉会直接报错）：

| 包 | 钉住 | 不钉的后果 |
| --- | --- | --- |
| `transformers` | `<5` | 5.x 改了 Trainer / DataCollator 接口，训练脚本按 4.x 写的 |
| `datasets` | `<4` | 5.x 需要 `huggingface_hub>=1.0`，与 transformers 4.55 的 `<1.0` 冲突 → `cannot import name BucketNotFoundError` |

### E.3 本机推荐路径：用 1.5B 把全链路跑通

目的不是拿交付指标，而是**验证数据、输出协议、评测口径、报告生成都正确**——这些和模型大小无关。

### E.4 如果坚持在本机训 7B（不推荐）

只有一条路：**4bit QLoRA + 压参数**。

```yaml
# config/lora_sft.yaml 改动项
load_in_4bit: true
batch_size: 1
grad_accum: 16        # 显存换时间的补偿
max_length: 1280      # 本项目样本估算最长约 1112 token，1280 刚好不截断
lora_rank: 8          # rank 减半，省一点优化器状态
```

```bash
# 训练前先确认显存够（8G 卡留 700MB 余量都不安全）
python train/finetune_lora.py --dry-run    # 关注「token 估算」和「估算截断」两行
python train/finetune_lora.py
```

预计 **6–10 小时**，且大概率中途 `CUDA out of memory`。真遇到就：

1. `max_length` 再降到 1024 或 896（会截掉少量长样本，看 dry-run 的截断比例决定）
2. 关掉所有占显存的程序（浏览器硬件加速、IDE、微信）
3. Windows 上把虚拟内存调到 ≥16 GB（4bit 加载瞬间会吃系统内存）
4. 还是不行 → 说明这张卡确实不适合，回 E.3 或上云

### E.5 本机系统内存别忽略

4bit 加载 7B 时，CPU 侧峰值要 5–7 GB 内存（先读 fp16 再量化）。
本机只有 16 GB 时，训练期间别开 Chrome 多标签、别开 Docker，
否则会看到 `Killed` 或系统卡死——这不是代码问题，是内存不够。

### E.6 8 GB 笔记本硬试 7B 的真实账（RTX 5060 Laptop 实测口径）

先把显存逐项算清（7B = 7.6B 参数）：

| 占用项 | 4bit QLoRA（seq 1024） | bf16 LoRA |
| --- | --- | --- |
| 权重 | ≈ 4.3 GB（nf4 + double quant） | ≈ 15.2 GB |
| LoRA 参数 + 优化器状态 | ≈ 0.4 GB（40M 参数） | ≈ 0.4 GB |
| 激活值（开梯度检查点） | 0.8–1.5 GB | 1.5–2.5 GB |
| CUDA 上下文 + 碎片 | 0.8–1.2 GB | 0.8–1.2 GB |
| Windows 桌面/浏览器占用 | 0.3–1.0 GB | 同左 |
| **合计** | **6.6–8.4 GB** | **18–20 GB** |

结论：**bf16 直接不用考虑；4bit 的合计值正好压在 8 GB 线上**，所以是「可能跑起来，也随时 OOM」。
实测可用显存 7.8 GB，留给你的余量不到 1 GB。

三个前几年常见、但现在**已经不再是拦路虎**的点（2026 年现状）：

- `bitsandbytes` 已有 Windows 轮子（`bitsandbytes-0.50.x-py3-none-win_amd64.whl`），能装
- `torch 2.8.0+cu128` 在官方源里有，RTX 50 系（sm_120）能正常跑
- 项目已在 `common/llm.py` 支持 `FTKB_LOAD_4BIT=1`，评测侧不用改

真正卡住的是**时间和显存余量**，不是软件：

| 环节 | 本机（8 GB / 15.2 GB 内存） | 云端 4090 24 GB |
| --- | --- | --- |
| 装 torch + bnb | 2.5 GB 下载 | 镜像已带 |
| 下 7B 模型 | 15.2 GB（按实测 ~0.8 MB/s 要 5 小时+，ModelScope 快些也要 1–3 小时） | 同 |
| 训练 756 条 × 3 epoch | 1.5–3 小时，且大概率中途 OOM 调参 | 50–80 分钟 |
| 成功率 | 约一半（seq 必须降到 512–768） | 高 |

所以本机的定位应该是：**用 1.5B 验证数据与流程（25–45 分钟，5–6 GB 显存），7B 上云**。
真要硬试，参数只能这样压：

```yaml
load_in_4bit: true
batch_size: 1
grad_accum: 16
max_length: 768        # 1024 起大概率 OOM；768 会截掉少量长样本
lora_rank: 8
lora_dropout: 0.1
```

并把 Chrome / IDE / 微信全部关掉（那 4 GB 空闲内存是硬约束）。
